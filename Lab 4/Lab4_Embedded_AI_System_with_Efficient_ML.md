### Step 2: Generate C code on ST Edge AI Developer Cloud

#### 2a. Where `mlp_mnist.onnx` came from

You are given this file, but you should know how it was made, because in a real project you would make it yourself.

The network is the same one from Lab 3: 784 inputs, a hidden layer of 128 with ReLU, and 10 outputs. In PyTorch:

```python
class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1  = nn.Linear(28*28, 128)
        self.relu = nn.ReLU()
        self.fc2  = nn.Linear(128, 10)

    def forward(self, x):
        return self.fc2(self.relu(self.fc1(x)))
```

Exporting it to ONNX is one call:

```python
model = MLP()
model.load_state_dict(torch.load("mlp_weights.pth", map_location="cpu"))
model.eval()

torch.onnx.export(
    model,
    torch.randn(1, 784),          # a fixed batch size of 1
    "mlp_mnist.onnx",
    export_params=True,           # write the weights into the file
    opset_version=13,
    do_constant_folding=True,
    input_names=["input"],
    output_names=["logits"],
    dynamo=False,
)
```

Two of those arguments matter more than the rest for embedded work:

**The batch size is fixed at 1, and there is no `dynamic_axes` argument.** A microcontroller has no memory allocator worth the name, so the code generator needs every buffer size to be known at compile time. A model with a flexible batch dimension will be rejected or silently forced to 1.

**`export_params=True`** writes the trained weights into the `.onnx` file. Without it you get the network's *shape* and no numbers — a model that runs and predicts nonsense.

#### 2e. Skip the quantization step

The next stage the tool offers you is **quantization** — converting the network's 32-bit floating point weights into 8-bit integers. **Skip it.** Move straight past it to the optimization step.

Two reasons:

**Quantization would break the comparison.** The whole point of this assignment is to put generated code next to the code you wrote in Lab 3. Yours used `float` throughout. If you quantize, you are no longer running the same arithmetic, and any speed difference you measure would be the arithmetic changing rather than the code generator doing its job.

**This network does not need it.** The float weights are about 400 KB against 2 MB of flash. There is nothing to save here.

Quantization is not a bad idea in general — it is one of the most effective things you can do to a network, and you will meet it properly in Assignment 3 with a model where 8-bit really is the difference between fitting and not fitting.

> **Question:** an 8-bit weight takes a quarter of the space of a 32-bit one. Name one thing besides flash size that would also improve, and one thing that would get worse.

#### 3b. How the build finds them

Open `CMakeLists.txt` and look at the block at the bottom. It was added for you, but you should understand every line of it, because in Assignment 3 you will replace the contents of `X-CUBE-AI` with a different model and this block is what keeps working.

```cmake
# --- ST Edge AI generated network -------------------------------
file(GLOB AI_APP_SOURCES CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/X-CUBE-AI/App/*.c)
target_sources(${CMAKE_PROJECT_NAME} PRIVATE ${AI_APP_SOURCES})

target_include_directories(${CMAKE_PROJECT_NAME} PRIVATE
    ${CMAKE_SOURCE_DIR}/X-CUBE-AI/App
    ${CMAKE_SOURCE_DIR}/X-CUBE-AI/Inc
)

file(GLOB AI_RUNTIME_LIB CONFIGURE_DEPENDS ${CMAKE_SOURCE_DIR}/X-CUBE-AI/Lib/*.a)
target_link_libraries(${CMAKE_PROJECT_NAME} stm32cubemx ${AI_RUNTIME_LIB} m)
```

| Line | What it does |
| ---- | ------------ |
| `file(GLOB AI_APP_SOURCES ...)` | Finds every `.c` in `App/` and puts the list in a variable |
| `target_sources(...)` | Adds those files to the things that get compiled |
| `target_include_directories(...)` | Lets `#include "network.h"` and `#include "stai.h"` be found |
| `file(GLOB AI_RUNTIME_LIB ...)` | Finds the `.a` runtime library |
| `target_link_libraries(... ${AI_RUNTIME_LIB} m)` | Links the runtime, and `m` — the maths library, which the runtime needs for `expf` and friends |

> **`file(GLOB ...)` runs when CMake configures, not when it builds.** That is why `CONFIGURE_DEPENDS` is there: it tells CMake to re-check these two folders before every build and reconfigure itself if the list of files has changed. Without it, CMake would use the list it found the first time — which, for a folder that was empty when you opened the project, is nothing at all.
>
> If you ever see the build succeed but the linker complain that `stai_runtime_init` is undefined, this is the cause: the generated `.c` files and the `.a` were never added to the build. Run **CMake: Delete Cache and Reconfigure** from the Command Palette (`Ctrl+Shift+P`) and build again.

`network.h` is generated specifically for *your* model. #### 4b. The buffers

In `USER CODE PV`:

```c
/* USER CODE BEGIN PV */
STAI_ALIGNED(STAI_NETWORK_CONTEXT_ALIGNMENT)
static stai_network network_context[STAI_NETWORK_CONTEXT_SIZE] = {0};

STAI_ALIGNED(STAI_NETWORK_ACTIVATION_1_ALIGNMENT)
static uint8_t activations[STAI_NETWORK_ACTIVATION_1_SIZE_BYTES];

STAI_ALIGNED(STAI_NETWORK_IN_1_ALIGNMENT)
static float nn_in[STAI_NETWORK_IN_1_SIZE];

STAI_ALIGNED(STAI_NETWORK_OUT_1_ALIGNMENT)
static float nn_out[STAI_NETWORK_OUT_1_SIZE];
/* USER CODE END PV */
```

Four buffers, and it is worth being clear about what each one is for.

**`network_context`** is the library's bookkeeping. It holds pointers to your other buffers, the current error code, and internal state. `stai_network` is just a typedef for `uint8_t`, so this is a plain byte array of the size the header tells you to use.

Notice how different this is from Lab 3. There, the network was three functions and four global arrays, and there was no "object" anywhere. Here the library needs somewhere to keep track of things across calls, and because it cannot call `malloc` on a microcontroller, **you** provide that memory.

**`activations`** is scratch space. When the network runs, the 128 hidden values have to live somewhere — this is that somewhere. In Lab 3 you wrote `float h[FC1_OUT_DIM];` inside `nn_infer` and it lived on the stack. This is the same idea, with two differences: the generator worked out the exact size needed for the whole network, and it is a global rather than a stack variable, so a large model cannot silently overflow your stack.

**`nn_in` and `nn_out`** are the network's input and output. You copy a digit into `nn_in`, run the network, and read the ten scores out of `nn_out`.

**`STAI_ALIGNED(n)`** forces a buffer to start at an address that is a multiple of `n`. The runtime reads these buffers with instructions that require aligned addresses, and an unaligned buffer produces a hard fault rather than a wrong answer. Leave these macros in place.

> **Question:** `STAI_NETWORK_IN_1_SIZE` is 784 and `STAI_NETWORK_OUT_1_SIZE` is 10. Where have you seen those two numbers before, and what are the corresponding names in Lab 3's `mlp_params.h`?

#### 4c. The initialization function

In `USER CODE 0`, above `main()`:

```c
static int ai_init(void)
{
    stai_return_code rc;

    /* 1. Bring up the runtime library itself. */
    rc = stai_runtime_init();
    if (rc != STAI_SUCCESS) {
        printf("runtime_init failed (%d)\r\n", (int)rc);
        return -1;
    }

    /* 2. Initialize this particular network in our context buffer. */
    rc = stai_network_init(network_context);
    if (rc != STAI_SUCCESS) {
        printf("network_init failed (%d)\r\n", (int)rc);
        return -1;
    }

    /* 3. Tell it where its scratch memory is. */
    stai_ptr acts[STAI_NETWORK_ACTIVATIONS_NUM] = { (stai_ptr)activations };
    rc = stai_network_set_activations(network_context, acts,
                                      STAI_NETWORK_ACTIVATIONS_NUM);
    if (rc != STAI_SUCCESS) {
        printf("set_activations failed (%d)\r\n", (int)rc);
        return -1;
    }

    /* 4. Tell it where the input and output buffers are. */
    stai_ptr ins[STAI_NETWORK_IN_NUM]   = { (stai_ptr)nn_in };
    stai_ptr outs[STAI_NETWORK_OUT_NUM] = { (stai_ptr)nn_out };
    stai_network_set_inputs(network_context, ins, STAI_NETWORK_IN_NUM);
    stai_network_set_outputs(network_context, outs, STAI_NETWORK_OUT_NUM);

    /* 5. Print what we are about to run. */
    printf("model       : %s\r\n", STAI_NETWORK_MODEL_NAME);
    printf("MACC        : %lu\r\n", (unsigned long)STAI_NETWORK_MACC_NUM);
    printf("input       : %d floats\r\n", (int)STAI_NETWORK_IN_1_SIZE);
    printf("output      : %d floats\r\n", (int)STAI_NETWORK_OUT_1_SIZE);
    printf("activations : %lu bytes\r\n",
           (unsigned long)STAI_NETWORK_ACTIVATION_1_SIZE_BYTES);
    printf("weights     : %lu bytes\r\n",
           (unsigned long)STAI_NETWORK_WEIGHTS_SIZE_BYTES);

    return 0;
}
```

Going through it:

**`stai_runtime_init()`** starts the runtime library — the code inside the `.a` file that actually performs the convolutions and matrix multiplications. It is called once per program, not once per network.

> Forgetting this call is the single most common mistake with this API. It does not fail at compile time and it does not fail here; it fails later, inside `stai_network_run`, with an unhelpful error code.

**`stai_network_init(network_context)`** sets up the context buffer for your specific model. After this call the context knows the shape of the network but has nowhere to put anything yet.

**`stai_network_set_activations`** hands over the scratch buffer. Note the shape of the call: an **array** of pointers, plus how many there are. Some models split their scratch space across several buffers so that you can place them in different memories; ours needs exactly one, and `STAI_NETWORK_ACTIVATIONS_NUM` is 1. Writing the code against the array form means it keeps working if you later deploy a model that needs more.

**`stai_network_set_inputs` / `set_outputs`** do the same for the input and output tensors. After these four calls the network knows where everything lives and is ready to run.

## Assignment 2: Explore the optimization options of ST Edge AI Developer Cloud

### Step 1: What the optimization setting actually controls

When a network runs, its layers produce intermediate results. Layer 1 of your MNIST network produces 128 hidden values; the ReLU then overwrites them; Layer 2 reads them and produces 10 outputs. Every one of those intermediate results needs somewhere to live while it is being used, and that somewhere is the **activations buffer** you allocated in Assignment 1.

The code generator has a choice to make about that buffer. It can:

- **give every intermediate result its own space**, which is simple and fast but needs more RAM, or
- **reuse the same space for several results** whose lifetimes do not overlap, which needs less RAM but may cost extra copying or force a less convenient memory layout.

That is the trade-off the optimization setting controls. The tool offers you roughly three positions on it:

| Setting | What it asks the generator to do |
| ------- | -------------------------------- |
| **Balanced** | A compromise — the default, and what you used in Assignment 1 |
| **Inference time** | Be as fast as possible, spend RAM if it helps |
| **RAM** | Use as little RAM as possible, accept being slower |

> The exact wording on the page may differ from these three names. What matters is that one option favours speed, one favours memory, and one sits between them.

#### 2d. Skip the quantization step again — but for a different reason

In Assignment 1 you skipped quantization because the network did not need it. Here you skip it because **it has already been done**. That is what `QDQ_INT8` in the file name means: the model arrives with 8-bit weights and with the scale factors needed to interpret them.

This matters for the rest of the assignment, so be clear about what quantization actually is.

A trained network's weights and activations are real numbers, typically in a range like −3 to +3. An 8-bit integer can only hold 256 distinct values. Quantization picks a **scale** and a **zero point** that map the real range onto those 256 slots:

```
real value  ≈  scale × (integer value − zero point)
```

Going the other way, to turn a real number into its 8-bit representation:

```
integer value  =  round(real value / scale)  +  zero point
```

Your generated `network.h` will contain the two constants for this model's input:

```c

#define STAI_NETWORK_IN_1_ZERO_POINT  (-14)
```

You will use exactly that second formula in Step 4 to turn camera pixels into something the network can accept.

> **Question:** with a scale of 0.018658 and a zero point of −14, what real value does the integer −128 represent? And +127? Those two numbers are the entire range of real values this network can see at its input.

#### 4c. The camera frame callback

This one is **already in the project**, left over from Lab 2. Find it in `USER CODE 0` and check it is still there:

```c
void BSP_CAMERA_FrameEventCallback(uint32_t Instance)
{
  frameFlag = 1;          /* the only place it is set */
}
```

Three lines, but how they work is worth being precise about, because your loop in Step 5 depends on it.

`BSP_CAMERA_Start` does **not** wait for a photograph. It tells the DCMI peripheral and the DMA controller to start filling `CameraBuf`, then returns immediately while the transfer carries on in the background. Something has to tell you when the frame is actually complete, and this function is that something.

`BSP_CAMERA_FrameEventCallback` is declared **weak** inside the BSP: the BSP supplies an empty version that does nothing, and any version you write replaces it. When the DMA finishes a frame it raises an interrupt, and the BSP's interrupt handler calls this function. **You never call it yourself** — the hardware does, at a moment you do not control.

So the handshake between your code and the interrupt runs like this:

| Who | Does what |
| --- | --------- |
| You | `frameFlag = 0;` — clear it |
| You | `BSP_CAMERA_Start(...)` — ask for a frame |
| Hardware | fills `CameraBuf` while your code carries on |
| Interrupt | this function runs and sets `frameFlag = 1` |
| You | `while (frameFlag == 0) { }` stops spinning |

Two details matter.

**Clear `frameFlag` before `BSP_CAMERA_Start`, never after.** If you start the capture first and clear the flag second, a frame that completes between those two lines sets the flag and you immediately wipe it. Your `while` loop then waits forever for a frame that has already arrived.

**`frameFlag` is declared `volatile`.** Look at it in `USER CODE PV`. Nothing inside `while (frameFlag == 0) { }` changes `frameFlag`, so a compiler is entitled to decide the condition can never become false and turn the loop into an unconditional infinite one. `volatile` tells it this variable can change behind its back and must be re-read from memory every time. Leave the keyword alone — the bug it prevents shows up when you change the build type, and not before.

#### 4e. The quantization lookup tables

Also in `USER CODE 0`, above `ai_init`:

```c
static void build_quant_luts(void)
{
    /* ImageNet normalisation, as used when this model was trained */
    static const float mean[3] = { 0.485f, 0.456f, 0.406f };
    static const float stdv[3] = { 0.229f, 0.224f, 0.225f };

    const float inv_s = 1.0f / (float)STAI_NETWORK_IN_1_SCALE;
    const int   in_zp = (int)STAI_NETWORK_IN_1_ZERO_POINT;

    for (int v = 0; v < 64; v++)
    {
        /* 5-bit red/blue and 6-bit green, expanded to 8 bits */
        int r8 = ((v & 0x1F) << 3) | ((v & 0x1F) >> 2);
        int g8 = (v << 2) | (v >> 4);
        int b8 = r8;

        int qr = (int)lrintf((((float)r8 / 255.0f - mean[0]) / stdv[0]) * inv_s) + in_zp;
        int qg = (int)lrintf((((float)g8 / 255.0f - mean[1]) / stdv[1]) * inv_s) + in_zp;
        int qb = (int)lrintf((((float)b8 / 255.0f - mean[2]) / stdv[2]) * inv_s) + in_zp;

        if (qr >  127) { qr =  127; }
        if (qr < -128) { qr = -128; }
        if (qg >  127) { qg =  127; }
        if (qg < -128) { qg = -128; }
        if (qb >  127) { qb =  127; }
        if (qb < -128) { qb = -128; }

        if (v < 32) { qlut_r[v] = (int8_t)qr; qlut_b[v] = (int8_t)qb; }
        qlut_g[v] = (int8_t)qg;
    }
}
```

This is the most interesting block in the assignment, so read it carefully.

Every pixel that goes into the network has to travel through four conversions:

1. **5 or 6 bits to 8 bits.** An RGB565 pixel stores red in 5 bits, green in 6, blue in 5. Shifting left and copying the top bits down into the empty places spreads the value across the full 0–255 range. This is the same expansion you did in Lab 2.
2. **0–255 to 0.0–1.0.** Divide by 255.
3. **ImageNet normalisation.** Subtract the mean and divide by the standard deviation of each colour channel across the ImageNet training set. The model was trained on inputs treated this way, so it expects them.
4. **Quantise to int8**, with the formula from Step 2d.

Doing all four for every pixel would mean 150 528 float divisions per photo, at a moment when you are already asking the board to do 150 million multiply-accumulates.

But notice: an RGB565 red channel has only **32 possible values**. Green has 64. Blue has 32. The four conversions depend on nothing except that value — so all of it can be computed once, at startup, into three small tables totalling **128 bytes**. After that, converting a pixel is three array lookups and no arithmetic at all.

> **Confirmation that the normalisation is right.** The smallest value this chain can produce is (0 − 0.485) / 0.229 = −2.118, and the largest is (1 − 0.406) / 0.225 = 2.640. The distance between them, divided by the 255 steps an int8 gives you, is 0.0186584 — which is the model's own `STAI_NETWORK_IN_1_SCALE` to seven digits. The quantisation range was chosen to fit exactly this preprocessing, which is how you can be sure these mean and standard deviation values are the right ones.

#### 4f. Camera frame to input tensor

```c
static void camera_to_tensor(const uint32_t *cam, int8_t *dst)
{
    const int X0    = (CAM_W - CROP) / 2;    /* 40 */
    const int Y0    = (CAM_H - CROP) / 2;    /* 0  */
    const int plane = NN_W * NN_H;           /* 50176 */

    int8_t *dr = dst;                        /* plane 0: red   */
    int8_t *dg = dst + plane;                /* plane 1: green */
    int8_t *db = dst + 2 * plane;            /* plane 2: blue  */

    for (int y = 0; y < NN_H; y++)
    {
        const int sy   = Y0 + (y * CROP) / NN_H;
        const int row  = sy * CAM_W;
        const int orow = y * NN_W;

        for (int x = 0; x < NN_W; x++)
        {
            const int sx  = X0 + (x * CROP) / NN_W;
            const int idx = row + sx;

            /* Two RGB565 pixels per 32-bit word - Lab 2, Assignment 2 */
            uint32_t w = cam[idx >> 1];
            uint16_t p = (idx & 1) ? (uint16_t)(w >> 16) : (uint16_t)(w & 0xFFFF);

            const int o = orow + x;
            dr[o] = qlut_r[(p >> 11) & 0x1F];
            dg[o] = qlut_g[(p >>  5) & 0x3F];
            db[o] = qlut_b[ p        & 0x1F];
        }
    }
}
```

Three things are happening in this one pass.

**Cropping.** `X0` is 40, so column `x` of the output comes from column `40 + something` of the frame — the leftmost and rightmost 40 columns are never read.

**Resizing.** `(x * CROP) / NN_W` maps output column `x` to a source column in the 240-wide crop. This is **nearest-neighbour** resizing: for each output pixel, pick the closest input pixel and use it unchanged. It is the cheapest method there is and perfectly adequate here.

**Colour conversion and quantisation**, via the three lookup tables from 4e.

The one part that needs explaining is the layout of the output. Look at where the three colours go:

```c
int8_t *dr = dst;                  /* bytes 0      .. 50175  */
int8_t *dg = dst + plane;          /* bytes 50176  .. 100351 */
int8_t *db = dst + 2 * plane;      /* bytes 100352 .. 150527 */
```

The red values of all 50 176 pixels come first, then all the green, then all the blue. Three separate images stacked one after another. This is called **channel-first** or **NCHW** layout, and your generated `network.h` says the model wants it:

```c
#define STAI_NETWORK_IN_1_FLAGS  (... | STAI_FLAG_CHANNEL_FIRST | ...)
#define STAI_NETWORK_IN_1_SHAPE  {1,3,224,224}
```

Models exported from PyTorch are usually channel-first. Models from TensorFlow are usually **channel-last** (NHWC), where the three colour bytes of each pixel sit together and you would write `dst[o * 3 + c]` instead.

> **This is the mistake that costs the most time in this assignment.** Both layouts compile, both run, and both produce ten plausible-looking class names. Only one of them is right. If your predictions look like confident nonsense that does not change much when you point the camera somewhere else, check this first.

#### 4g. Printing the top five

```c
static void print_top5(const int8_t *out, uint32_t ms)
{
    int idx[TOP_K];
    int val[TOP_K];

    for (int k = 0; k < TOP_K; k++) { idx[k] = -1; val[k] = -1000; }

    for (int i = 0; i < NN_CLS; i++)
    {
        const int v = out[i];
        for (int k = 0; k < TOP_K; k++)
        {
            if (v > val[k])
            {
                for (int m = TOP_K - 1; m > k; m--) { val[m] = val[m-1]; idx[m] = idx[m-1]; }
                val[k] = v;
                idx[k] = i;
                break;
            }
        }
    }

    printf("\r\n--- inference %lu ms ---\r\n", (unsigned long)ms);
    for (int k = 0; k < TOP_K; k++)
    {
        if (idx[k] < 0) continue;
        const float score = (float)STAI_NETWORK_OUT_1_SCALE *
                            ((float)val[k] - (float)STAI_NETWORK_OUT_1_ZERO_POINT);
        printf("  %d. [%3d] %-30s %8.3f\r\n",
               k + 1, idx[k], imagenet_labels[idx[k]], (double)score);
    }
    printf("Press USER to classify again.\r\n");
}
```

This is your `argmax` from Lab 3, generalised from one winner to five. It keeps a sorted list of the best five seen so far; each new value that beats an entry is inserted and everything below it shifts down.

Two details worth noticing.

**The ranking is done on the raw `int8` scores**, not on dequantised values. That is valid because dequantisation is `scale × (value − zero_point)` with a positive scale — a straight line that never changes the order. Only the five winners are converted into real numbers, and only so that they can be printed.

**The class index is printed as well as the name.** `[954]` next to `banana` lets you check the label file directly when a result looks wrong.

### Step 5: Write the loop

Everything is ready. The loop goes in `USER CODE WHILE` — the body of `while(1)` — because unlike every earlier lab this program waits for the user and runs again each time.

```c
  /* USER CODE BEGIN WHILE */
  while (1)
  {
    /* 1. If the button is not pressed, do nothing. Go round again.
     *
     *       if (!button_pressed()) continue;
     *
     * 2. It is pressed. Debounce it:
     *       - HAL_Delay(50);
     *       - then wait, doing nothing, until button_pressed() is false.
     *    Without this you get several classifications from one press.
     *
     * 3. Turn the green LED on so the user knows something is happening.
     *    LED_GREEN is active low:
     *       HAL_GPIO_WritePin(LED_GREEN_GPIO_Port, LED_GREEN_Pin, GPIO_PIN_RESET);
     *
     * 4. Take one photo. The first three lines are the same as Lab 2,
     *    but there is now a fourth:
     *       frameFlag = 0;
     *       BSP_CAMERA_Start(0, (uint8_t *)CameraBuf, CAMERA_MODE_SNAPSHOT);
     *       while (frameFlag == 0) { }
     *       BSP_CAMERA_Stop(0);
     *
     *    See the note below on why the Stop is needed here and was not
     *    needed in Lab 2.
     *
     * 5. Convert the frame into the network's input tensor:
     *       camera_to_tensor(CameraBuf, nn_in);
     *
     * 6. Read HAL_GetTick() into t0, run the network, read HAL_GetTick()
     *    into t1:
     *       stai_return_code rc = stai_network_run(network_context,
     *                                              STAI_MODE_SYNC);
     *
     * 7. Turn the green LED off.
     *
     * 8. If rc is not STAI_SUCCESS, print the error from
     *    stai_network_get_error(network_context) and go round again.
     *
     * 9. Otherwise print the results:
     *       print_top5(nn_out, t1 - t0);
     */
    /* USER CODE END WHILE */

    /* USER CODE BEGIN 3 */
  }
  /* USER CODE END 3 */
```

> **Hints:**
>
> - `HAL_GetTick()` returns milliseconds since startup. Use it rather than `TIM2->CNT` here: this inference takes seconds, and TIM2's 32-bit cycle counter wraps around every 26.8 seconds.
> - Step 2's "wait until released" is a `while` loop with an empty body: `while (button_pressed()) { }`.
> - The LED is active low on this board, so `GPIO_PIN_RESET` turns it **on**.
> - `camera_to_tensor` writes straight into `nn_in`, which points inside the activations buffer. There is no copy afterwards — the network reads what you just wrote.

> **Why the snapshot must finish before you preprocess.** `BSP_CAMERA_Start` returns immediately; the DMA is still filling `CameraBuf` in the background. `frameFlag` is set by `BSP_CAMERA_FrameEventCallback` when the frame is complete. If you skip the `while (frameFlag == 0)` wait, you convert half an old picture and half a new one.

> **Why `BSP_CAMERA_Stop(0)` is needed, and why Lab 2 did not need it.** Lab 2 took exactly one photograph and then sat in an empty `while(1)` forever. This program takes a new one every time you press the button, and that is the difference.
>
> On the STM32U5 the camera is fed by a GPDMA **linked-list** queue, set up once in `USER CODE 2` by `MX_DCMIQueue_Config()` and `HAL_DMAEx_List_LinkQ()`. A snapshot consumes that queue. If you never stop the camera, the second `BSP_CAMERA_Start` does not begin a new capture, `frameFlag` is never set, and your program sits in `while (frameFlag == 0)` forever.
>
> Calling `BSP_CAMERA_Stop(0)` once the frame has arrived leaves the camera in a state the next `Start` can work from.
>
> **The symptom is worth recognising**, because it looks like something else entirely: the first press works perfectly, the second press appears to do nothing at all, and the board seems to have crashed or stopped reading the button. It has not — it is waiting for a frame that will never come.

> **Optional, but it saves time when something goes wrong.** An infinite wait is indistinguishable from a crash when all you can see is the serial output. Giving the wait a timeout makes it report itself instead:
>
> ```c
> uint32_t started = HAL_GetTick();
> while (frameFlag == 0)
> {
>     if (HAL_GetTick() - started > 2000) { printf("camera timeout\r\n"); break; }
> }
> ```

| `STAI_NETWORK_IN_1_SCALE` / `_ZERO_POINT` | Quantisation constants for the input, on int8 models |
| `STAI_NETWORK_OUT_1_SCALE` / `_ZERO_POINT` | Quantisation constants for the output |
| `STAI_NETWORK_IN_1_FLAGS` | Includes `STAI_FLAG_CHANNEL_FIRST` or `STAI_FLAG_CHANNEL_LAST` |
| `STAI_ALIGNED(n)` | Forces the next buffer to start on an `n`-byte boundary |

`stai_network` is `uint8_t`. `stai_ptr` is `uint8_t *`. `STAI_SUCCESS` is 0.
